One Expired Cache Key Can Become Five Thousand Database Calls

A cache expiry looks like deletion, but under load it behaves like a schedule. Every reader reaches the same boundary with the same information.

Part 1

The Simple Cache Code Is Almost Embarrassingly Obvious

The schema more or less writes itself. Keep a value. Keep an expiry. When the value is missing, rebuild it and put it back.

Java
Value get(String key) {
    Value value = cache.get(key);
    if (value == null || value.isExpired(now())) {
        value = origin.load(key);
        cache.put(key, value, ttl);
    }
    return value;
}

This is not foolish code. It is the pattern most teams mean when they say cache aside. It only breaks when many callers make the same reasonable decision together.

Trace
read key
miss
query database
write cache
return value

The single request trace looks perfect. One user pays the cost, the next user gets the cached value, and the database avoids repeated work. The trace stops being true when the miss path takes longer than the gap between readers.

Part 2

The Bug Is A Boundary Shared By Everyone

A cache expiry is a public deadline. Every reader sees the same wall clock and the same missing value.

Timeline
09:00:00.000  key expires
09:00:00.001  reader 1 misses
09:00:00.001  reader 2 misses
09:00:00.001  reader 3 misses

The XFetch paper gives the simple arithmetic: if a cache item is accessed 10 times per second and recomputation takes 3 seconds, then 30 requests can recompute it. The cache did not reduce work. It synchronized it.

That example does not need exotic traffic. Ten requests per second is an ordinary hot page. Three seconds is an ordinary expensive regeneration. The multiplication is the outage hiding inside normal numbers.

Part 3

Facebook Names This A Thundering Herd

Facebook's memcache paper says its system processed over a billion requests per second and stored trillions of items. At that scale, a hot key is not just a local inefficiency.

Trace
one key
many readers
one expiry
many database trips

The paper describes a thundering herd as what happens when heavy read and write activity repeatedly invalidates a key, so reads fall back to the more costly path.

Notice the write side in that sentence. This is not only about a key aging out peacefully. A busy object can be invalidated repeatedly by writes, and each invalidation sends readers back toward the database before the cache has a stable answer again.

Part 4

A Lease Makes The Miss Conditional

Facebook's fix is to make a cache miss carry authority. Memcached gives one client a lease token for the key. The token is 64 bits, and the client must present it when writing the regenerated value.

Trace
reader A misses -> receives lease token
reader B misses -> told to wait
reader C misses -> told to wait
reader A writes -> token is verified

This changes the question from who noticed the miss to who is allowed to repair it.

Rule
without lease: every miss can rebuild
with lease:    one miss can rebuild

For herds, Facebook adds a small rule: by default, memcached returns a token only once every 10 seconds per key. Other readers receive a special notification telling them to wait briefly.

In the paper's measurement for herd prone keys, peak database query rate fell from 17K/s without leases to 1.3K/s with leases. The number matters because databases are provisioned for peaks.

Part 5

XFetch Fixes The Cliff Before It Arrives

Leases control the miss after it happens. XFetch asks a stranger question: what if the cache refreshes before the hard expiry?

XFetch sketch
value, delta, expiry = cache.read(key)
gap = -delta * beta * log(rand())
if now + gap >= expiry:
    value = origin.load(key)

The delta is the last recomputation time. The random gap is exponential. The default beta in the paper is 1.

Scaling by recomputation time is what makes the rule practical. A value that takes longer to rebuild starts asking for earlier refreshes. A cheap value can wait closer to expiry because its stampede window is smaller.

Shape
hard expiry:
                 |||||||||||||||||| origin

exponential early expiry:
          |       |    |       |     origin

In the paper's experiment with 10 second regeneration, exponential gaps produced stampedes mostly of size 1 or 2, with none larger than 8. Uniform gaps were closer to 10 on average and sometimes 20 or more.

Part 6

The Local Run Makes The Claim Executable

The Spring Boot repo simulates one hot key, 1,000 readers, 5 expiry cycles, a 1,000 ms TTL, and a 100 ms recomputation time.

CSV
strategy,origin_fetches,max_origin_fetches_per_expiry
naive,5000,1000
lease,5,1
xfetch,25,6

These are local measurements from the repo, not Facebook production numbers. They are useful because they make the shape testable.

Invariant
naive  = readers * expiry cycles
lease  = one repair per expiry cycle
xfetch = a few early repairs before the cliff

The benchmark is intentionally narrow. It does not claim a universal reduction factor. It answers one concrete question: when a single hot key expires under 1,000 readers, does the strategy make origin work scale with readers or with repair windows?

Part 7

The Tradeoff Is Control Complexity

Leases add server cooperation. XFetch adds early work. Both are real costs.

Tradeoff
more coordination -> fewer duplicate origin calls
more early refresh -> fewer synchronized misses

The wrong trade is pretending expiry is free. A cache is a shared coordination system once enough clients depend on it.

XFetch pays in earlier work. Leases pay in coordination. Naive cache aside pays at the worst moment, because the bill arrives exactly when the key is hot and empty.

Some products can serve stale data while the repair runs. Some must block. Some can return a partial response. The lease only decides who rebuilds. The product still decides what everyone else experiences while the rebuild is happening.

Part 8

The Part That Generalizes

The system lesson is not use leases or use XFetch. The lesson is that a shared deadline can be a hidden broadcast.

Mental model
wrong model:
expiry removes one cached value

better model:
expiry schedules many clients at once

Once you see expiry as scheduling, the fixes become clearer. Either elect one repairer, or spread repair attempts before the deadline.

This generalizes beyond caches. Cron jobs, retry timers, deployment waves, and client reconnect loops all become dangerous when many machines share the same trigger. The fix is often the same: ownership, jitter, or a budgeted gate.

A cache miss is not only a lookup outcome. It is also permission to create expensive work.

Question
naive question:
is the value missing?

better question:
who is allowed to rebuild it?

The cliff is not made of bad requests. It is made of good requests arriving with the same information.
