High-Level Design

SyncDrop

A private cross-device inbox. Drop text, links, or files on one device and pick them up on another — everything signed into the same Google account stays in sync. Items expire after 7 days unless pinned.

System Overview

SyncDrop is a serverless application on AWS with a Next.js PWA frontend. There is no server to manage — Lambda functions respond to API requests, DynamoDB stores the data, and S3 holds uploaded files. Authentication is handled entirely by Cognito with Google as the identity provider.

Components

Frontend

Next.js PWA

App Router, TypeScript, Tailwind. Installable as a PWA. Polls /sync every 5s. IndexedDB cache, optimistic updates.

API Layer

API Gateway (REST)

JWT authorizer validates Cognito tokens on every route. Stage throttle 10 req/s, usage plan quota 50k/day.

Compute

Lambda (Java 21)

Plain handlers, no framework. SnapStart for cold start reduction. Static SDK clients initialized once.

Database

DynamoDB

Single-table design. PK/SK pattern for users, items, todos. TTL auto-expires items. LSI on updatedAt for sync.

Storage

S3

Private bucket for file uploads (max 25 MB). All access via presigned URLs. Block all public access.

Auth

Cognito + Google

Google sign-in only. User identity from JWT sub claim. No email/password flow. Testing mode during development.

Data Flow

Creating a text item: Browser sends POST /v1/items with the JWT. API Gateway validates the token, forwards to Lambda. Lambda reads the user's sub from the JWT, writes to DynamoDB with a 7-day TTL, returns the created item.

File upload (two-phase): Browser requests a presigned upload URL. Lambda checks quotas, creates a pending item row, returns the presigned POST URL. Browser uploads directly to S3. Browser calls /complete to mark the item visible.

Sync: Each device polls GET /v1/sync?since=<timestamp>. Lambda queries the updatedAt LSI for all records newer than the timestamp, including soft-deleted tombstones so other devices learn about deletions.

Low-Level Design

Data Model & API

Single-table DynamoDB design, REST API contract, and the key patterns that make each piece work.

DynamoDB Table: syncdrop

Every entity — user profiles, items, and todos — lives in one table with a composite primary key. The partition key (PK) groups records by user; the sort key (SK) identifies the entity type and provides ordering.

Key Patterns

Why Single Table?

With provisioned capacity at 1 RCU / 1 WCU, every table costs money. A single table means one set of capacity units serves all access patterns. The PK groups everything by user, so a query for "all of user X's items" is a single partition scan — fast and cheap.

Interview Concept

DynamoDB Single-Table Design

Unlike relational databases where you normalize into many tables, DynamoDB encourages denormalization. You model access patterns, not entities. The PK+SK combination lets you store different entity types together and query them efficiently.

Key insight: You pick your keys based on the questions you need to answer, not the shape of the data. "Give me all items for user X, newest first" becomes a simple Query on PK=USER#X with SK begins_with ITEM# in reverse order.

TTL: The Easiest Thing to Get Wrong

expiresAt is in epoch seconds. Every other timestamp is in epoch milliseconds. DynamoDB TTL expects seconds — if you accidentally store milliseconds, items won't expire for thousands of years.

EventexpiresAt Value

Item pinnednow_seconds + 90 days
Item unpinnedcreatedAt_seconds + 7 days
Todo completeddoneAt_seconds + 30 days
Todo not doneabsent (no TTL)

Local Secondary Index

An LSI on updatedAt powers the sync endpoint. Same partition key (PK), different sort key (updatedAt). This lets the sync query ask: "for user X, give me everything changed since timestamp T" — a single, efficient range query.

API Contract

Base path /v1. Every route requires a Cognito JWT in the Authorization header.

Core Rules

User identity comes from the JWT sub claim, never from the request body. Any code that reads a user ID from the request body is a security bug. The API Gateway validates the JWT before Lambda even runs.

File Upload Flow (Two-Phase)

Interview Concept

Presigned URLs

Instead of proxying file uploads through Lambda (which has a 6 MB payload limit and charges per ms), the client uploads directly to S3 using a presigned POST URL. Lambda just generates the signed URL with a content-length-range condition — the client can't upload more than it declared.

Why two-phase? The item row is created with pending: true when the URL is issued. The client calls /complete after uploading. This prevents the database showing items whose files never arrived. Uncompleted items are swept by TTL.

Soft Delete Pattern

Deleting an item sets deleted: true and updates updatedAt. The row stays in DynamoDB so other devices learn about the deletion via the sync query. TTL eventually removes the tombstone. For files, the S3 object is deleted immediately and bytesUsed is decremented atomically.

Interview Concept

What is AWS CDK?

CDK (Cloud Development Kit) lets you define cloud infrastructure using a real programming language instead of writing JSON/YAML templates. You write Java classes that describe your DynamoDB table, Lambda function, API Gateway, etc. CDK compiles this into a CloudFormation template and deploys it.

Why it matters: Infrastructure as Code means your entire cloud setup is version-controlled, reviewable, and reproducible. You can destroy and recreate your entire stack from a single command. No clicking around the AWS console.

// This Java code creates a DynamoDB table in AWS
Table table = Table.Builder.create(this, "SyncDropTable")
    .tableName("syncdrop")
    .partitionKey(Attribute.builder()
        .name("PK").type(AttributeType.STRING).build())
    .billingMode(BillingMode.PROVISIONED)
    .readCapacity(1)
    .writeCapacity(1)
    .build();
Interview Concept

What is Maven?

Maven is a build tool for Java. It manages dependencies (downloading libraries your code needs), compiles your source code, runs tests, and packages everything into a JAR file. The pom.xml file describes your project and its dependencies.

Key command: mvn package compiles the code and produces a JAR. For Lambda, we use the maven-shade-plugin to create a "fat JAR" — a single file containing your code and all its dependencies.

Interview Concept

Google OAuth 2.0

OAuth lets users sign in with their existing Google account instead of creating a new username/password. The flow: user clicks "Sign in with Google" → Google shows a consent screen → user approves → Google redirects back with an authorization code → Cognito exchanges it for tokens.

Why Cognito + Google? Cognito handles the OAuth flow, token management, and JWT generation. We never see the user's Google password. We just get a JWT with a sub claim (a unique user identifier) that we use as the partition key in DynamoDB.

Created Google Cloud project "SyncDrop" with OAuth 2.0 credentials. In Testing mode, only specified test users can sign in — prevents strangers from using the app during development.

Interview Concept

What is AWS Lambda?

Lambda runs your code without managing servers. You upload a JAR, specify the handler class, and AWS runs it when triggered (in our case, by an API Gateway request). You pay only for execution time.

Cold starts: The first invocation after a period of inactivity takes longer because AWS needs to set up the execution environment and load your JAR. SnapStart pre-initializes a snapshot of your function, reducing cold start time from ~5s to ~200ms for Java.

Static clients: The DynamoDB and S3 SDK clients are declared as static final fields. They're initialized once when the Lambda container starts and reused across invocations — creating a new client per request would waste 200ms+ each time.

public class ApiHandler implements RequestHandler<...> {
    // Created ONCE when the container starts, reused across invocations
    private static final DynamoDbClient dynamoDb = DynamoDbClient.create();
    private static final S3Client s3 = S3Client.create();

    @Override
    public APIGatewayProxyResponseEvent handleRequest(...) {
        // This runs on every API request
    }
}
Interview Concept

REST API Gateway vs HTTP API

AWS offers two types of API Gateway. We chose REST API because it supports usage plans with daily quotas (50,000 requests/day). HTTP API is cheaper and faster but doesn't have this feature.

JWT Authorizer: API Gateway validates the Cognito JWT token before your Lambda even runs. Invalid tokens get a 401 immediately. This means your Lambda code never handles authentication — it just reads the user ID from the already-validated token.

Gotcha: New AWS accounts have a Lambda concurrency limit of 10. Reserving 5 for our function would drop unreserved below the minimum of 10, causing the deploy to fail. Solution: deploy without reserved concurrency now, request a quota increase, then add it back.
Interview Concept

How AI Agents Fit In

This project is being built with AI coding agents (Claude, Codex). The workflow: the human writes the spec (PROJECT.md), then the agent writes the code in each session. PROGRESS.md is the handoff file — agents have no memory between sessions, so it records what's done, what's not, and gotchas encountered.

Key pattern: The spec is the contract. The agent follows it exactly. If the agent thinks the spec is wrong (like the HTTP API / daily quota conflict), it flags it and stops rather than making a unilateral decision. The human decides.

Interview Concept

Cognito User Pools

A Cognito User Pool is a managed user directory. Instead of building your own user database, login forms, password reset, MFA, and session management, Cognito handles all of it. You configure identity providers (Google, Facebook, SAML, etc.) and Cognito issues JWTs.

The flow: User clicks "Sign in with Google" → redirected to Cognito's hosted UI → Cognito handles the Google OAuth exchange → Cognito issues its own JWT tokens (id_token, access_token, refresh_token) → your frontend stores the tokens and sends them with API requests.

Interview Concept

Cognito Authorizer on API Gateway

A Cognito authorizer on REST API Gateway validates the JWT in the Authorization header before the request ever reaches Lambda. If the token is expired, malformed, or from the wrong user pool, API Gateway returns 401 immediately — Lambda never runs and you never pay for it.

How Lambda gets user info: API Gateway passes the decoded JWT claims in requestContext.authorizer.claims. Lambda reads claims.sub for the user ID and claims.email for the email. The Lambda code never validates the token itself — that's already done.

// In the Lambda handler — the JWT is already validated by API Gateway
Map<String, String> claims = request.getRequestContext()
    .getAuthorizer().get("claims");
String userId = claims.get("sub");    // unique, stable user ID
String email = claims.get("email");   // from Google profile
Interview Concept

SSM Parameter Store for Secrets

AWS Systems Manager Parameter Store is a free key-value store for configuration. We store the Google OAuth client ID and secret there instead of in code or environment variables. CDK reads them at deploy time and passes them to the Cognito configuration.

Gotcha discovered: CloudFormation can't pass SSM SecureString parameters to all resource types (including Cognito identity providers). For this personal project, we store the Google secret as a plain String — it's still IAM-protected, and the secret alone is useless without the correct OAuth redirect URI registered in Google Console.

Interview Concept

GET /v1/me — Auto-Create Pattern

The /v1/me endpoint returns the user's profile. On first call, it creates the profile in DynamoDB using a conditional write (attribute_not_exists(PK)) to prevent race conditions from multiple devices signing in simultaneously. Subsequent calls just return the existing record.

Why conditional write? If two devices sign in at the exact same moment, both would try to create the profile. The condition ensures only the first write succeeds — the second gets a ConditionalCheckFailedException and falls through to reading the existing profile.
