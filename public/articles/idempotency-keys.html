Fifty payment requests. One charge.

An idempotency key turns an ambiguous network retry into a replay of one completed payment result.

01 / The naive solution

The Obvious Handler Charges Every Request

The schema for a payment endpoint almost writes itself. Receive an amount. Create a charge. Return its identifier. The handler can be small enough to feel finished before the interesting failure has even been considered.

Start with the sympathetic version. One call to the handler creates one ledger entry and returns it. There is no obvious bug in the local control flow.

PaymentResponse charge(PaymentRequest request) {
    String chargeId = ledger.createCharge(request);
    return PaymentResponse.created(chargeId);
}

The arithmetic also looks harmless when requests and intentions remain aligned.

one request
    ↓
one ledger write
    ↓
one response

But HTTP requests are delivery attempts, not business intentions. Once those two concepts separate, the function has no memory that it has already done the work.

02 / Ambiguous delivery

The Failure Happens After Success

Alice confirms a purchase from a train. The payment service commits the charge. Before its response crosses the mobile network, the connection disappears. Her phone sees a timeout, but a timeout cannot say whether the server acted.

Alice → payment service → ledger: charge committed
Alice ← payment service: response lost
Alice → payment service: retry

The second request is indistinguishable from a second purchase to the naive handler. It performs its only behavior again.

client knowledge:  unknown
server state:      charge exists
safe to retry?:    impossible to infer from silence

Stripe’s engineering article on robust APIs describes this exact ambiguity: an operation can complete even when its result never reaches the client. The dangerous part is not failure itself. It is disagreement about whether failure happened.

03 / Request semantics

A Retry Is a Question, Not a New Command

The useful interpretation of a retry is: “What happened to the operation already named by this request?” The naive server instead hears: “Please perform this operation now.” An idempotency key changes the grammar of the conversation.

without a key:  perform a payment
with a key:     perform or recall payment <order-key>

The client must keep the key stable across attempts. It should generate a new key only for a genuinely new intended payment.

POST /payments
Idempotency-Key: order-cart-alpha

amount_cents=<amount>&currency=usd

The key is not a request identifier assigned by the server. It is a name chosen by the client for one unit of intent, carried into every uncertain retry.

04 / Stable identity

One Key Names One Intention

A strong key can be random, or derived from a durable business identifier such as a cart. Stripe suggests UUID style random values and documents that keys can be up to 255 characters. The uniqueness mechanism matters less than the boundary it names.

order-cart-alpha → charge this cart in usd
order-cart-beta  → charge a different cart in usd

The mapping must not drift. If the caller sends the same key with a different amount, accepting it would make the stored answer lie about the new request.

same key + same payload      → replay is safe
same key + different payload → reject the misuse
different key                → a new intention

That is why the server stores a request fingerprint beside the result. A key identifies the operation. The fingerprint proves that later attempts still describe it.

05 / Atomic ownership

Reserve the Key Before Touching the Ledger

Checking for a key and then inserting it is not enough. Two workers can both observe absence before either writes. The claim depends on an atomic reservation.

worker A: key absent ─┐
worker B: key absent ─┼→ both charge
worker A: store key  ─┤
worker B: store key  ─┘

Redis expresses the reservation as a conditional write. The repository’s Redis adapter uses NX so only one caller creates the processing marker, plus a time to live so abandoned state eventually expires.

SET idempotency:<key> <processing-record> NX PX <ttl>

The winner is allowed to touch the ledger. Every loser must inspect or await the record instead of starting another charge.

06 / State machine

The First Request Owns the Work

The repository models three useful stored states: missing, processing, and completed. Payload mismatch is a decision made while reading either stored state.

MISSING    --reserve--> PROCESSING
PROCESSING --commit---> COMPLETED
COMPLETED  --retry----> COMPLETED

Only the transition from missing to processing grants ownership. The owner token prevents an old worker from overwriting a record acquired later after expiration.

reserve(key, fingerprint)
    acquired    → create the charge
    in progress → wait for the owner
    completed   → replay the result
    mismatch    → reject the request

This state machine is the core of the demo. The local adapter uses an atomic map operation. The Redis adapter uses conditional set and a compare and set script. Both express the same ownership rule.

07 / Durable replay

Replays Return the Same Answer

Preventing a second charge is necessary but insufficient. A retrying caller still needs a definitive answer. The completed record therefore stores the status and body produced by the winning attempt.

{
  "fingerprint": "<request-hash>",
  "status": "created",
  "body": "<winning-response>"
}

The second caller does not manufacture a fresh success. It receives the recorded result of the first execution.

<stored-status-line>
Idempotent-Replayed: true

<stored-response-body>

Stripe documents the same broad behavior: it saves the first result for a key and returns that result to subsequent matching attempts, even when the stored result represents a 500 error. A retry is a replay, not an instruction to improve history.

08 / Payload integrity

Payload Fingerprints Prevent Key Reuse

The demo canonicalizes the amount and currency, then hashes that representation. The specific hash is less important than stable serialization. If two workers serialize equivalent requests differently, they can create false mismatches.

canonical request = amount + ":" + lowercase(currency)
fingerprint       = SHA-256(canonical request)

On a matching replay, the stored body is safe to return. On mismatch, the service refuses to reinterpret the existing key.

{
  "error": "idempotency_key_reused_with_different_payload"
}

Production canonicalization must cover every parameter capable of changing the business effect. Omitting a field from the fingerprint is equivalent to pretending that field does not matter.

09 / Concurrency policy

Concurrent Duplicates Need an Explicit Policy

The demo makes concurrent duplicates wait for the owner, then replays the completed result. This makes the single effect property easy to observe in one burst.

50 callers → one owner → one charge
           ↘ 49 waiters → one stored response

That behavior should not be attributed to Stripe. Stripe’s API reference says a request that conflicts with another request executing concurrently is not saved as an idempotent result because endpoint execution did not begin. The caller can retry after the conflict.

this demo: concurrent duplicate → wait, then replay
Stripe docs: concurrent conflict → retryable conflict
shared property: one key must not authorize duplicate work

The transport policy can differ while the business invariant remains the same.

10 / Retention contract

Expiration Reopens the Door

Remembering every key forever would create unbounded storage. Stripe documents a 24 hour window for safe retries and explains that keys expire after that period. A reused key outside its retention window can name a new execution.

inside retention: same key → recall old result
after expiration: same key → no record exists

This is a contract, not housekeeping trivia. Clients must keep their retry horizon inside the server’s retention horizon.

The required relationship The client retry deadline must not exceed the server key retention deadline.

If a client can wake after the record has expired and retry blindly, idempotency no longer distinguishes the old intention from a new request carrying a recycled name.

11 / System boundary

Redis Coordinates but Cannot Transact the World

Redis can choose one owner and hold the response. It cannot automatically join the transaction of an unrelated payment ledger. There are still two durable facts to write.

fact A: the charge exists in the ledger
fact B: the idempotency result exists in Redis

Conditional set makes ownership atomic inside Redis. The compare and set completion script prevents the wrong owner from replacing the marker. Neither operation commits the external ledger write.

Redis transaction boundary  | reservation + stored response
Ledger transaction boundary | monetary side effect
                             | ← gap remains

Calling that gap “exactly once” does not close it. The implementation has to recover across it.

12 / Honest failure

The Crash Window Is the Honest Part

The most important adversarial test crashes after the ledger creates the charge but before the response is stored. The handler removes its abandoned reservation. A retry acquires the key and creates another charge.

reserve → charge committed → CRASH → response never stored
retry   → reserve again     → second charge

The passing test asserts that two charges appear in this deliberately broken case. That is not a celebration of failure. It is executable documentation of the boundary a Redis only pattern cannot cross.

SETNX prevents simultaneous owners.
SETNX does not atomically commit an external side effect.

A credible demo should expose where its guarantee ends. Hiding the crash window would teach a stronger claim than the code can support.

13 / Executable evidence

The Measurement Should Assert a Property

This topic is about correctness, so the benchmark does not pretend that local latency generalizes. It fires real concurrent HTTP requests and counts business effects.

Naive mode 50 charges from 50 requests
Idempotent mode 1 charge plus 49 replays 
mode              requests  successes  charges  replays
naive                   50         50       50        0
idempotency_key         50         50        1       49

Those values came from the companion repository’s benchmark.csv, produced by the default Java run. Every caller received a successful response. The difference was the number of ledger writes.

mode,requests,successful_responses,created_charges,replayed_responses
naive,50,50,50,0
idempotency_key,50,50,1,49

The property can be stated without a stopwatch.

created_charges(idempotent burst) = 1
response_bodies(unique)           = 1

That is stronger evidence for the article’s claim than a fragile speed comparison on one laptop.

14 / Small mechanism

The Dumb Version Fits in One State Machine

The core handler is small. Reserve the key. Branch on the stored state. Only the owner calls the ledger. Then store the response.

Decision decision = store.reserve(key, fingerprint, ttl);
return switch (decision.state()) {
    case COMPLETED -> replay(decision.response());
    case MISMATCH -> rejectKeyReuse();
    case IN_PROGRESS -> awaitOwner(key, fingerprint);
    case ACQUIRED -> chargeAndStore(decision.owner());
};

The complexity is not in syntax. It is in choosing the state boundary, keeping request identity stable, and specifying crash behavior.

mechanism code: reservation + fingerprint + replay
evidence:       property tests + CSV
honesty:        crash test + Limits section

Small code is useful here because every branch corresponds to a claim a reviewer can challenge.

15 / Build one

Build the Dumb Version Yourself

Run the whole experiment with one command. Java starts a local HTTP server, launches concurrent clients, prints the result, and writes the CSV.

./gradlew run

Then implement it again without copying the store. The task list is short enough to hold in your head.

[ ] name one business intention with one key
[ ] atomically reserve that key
[ ] fingerprint every effect changing field
[ ] persist the winning status and body
[ ] replay matches and reject mismatches
[ ] expire records under an explicit contract

Add Redis only after the in memory state machine is correct. Infrastructure cannot repair an ambiguous protocol.

16 / Adversarial proof

Then Break It

Correctness claims become interesting under adversarial orderings. The repository turns each research question into a real test.

same key, 50 simultaneous attempts
same key, first response lost
same key, different amount
different keys, same payload
same key, expired record
crash after ledger write

The first tests defend the useful property. The last test defines its limit. Run them whenever the reservation or storage code changes.

./gradlew test

If the crash test unexpectedly reports one charge, inspect why. You may have genuinely introduced a shared transaction, or you may only have stopped simulating the dangerous ordering.

17 / Durable recovery

Production Adds Recovery, Not Magic

There are several honest ways to close or manage the crash gap. Put the idempotency record and charge in the same database transaction. Write a durable command first and let one worker apply it. Or reconcile incomplete records against a ledger whose own operation identifier is unique.

option A: idempotency row + ledger row in one transaction
option B: durable command → worker → durable result
option C: unique operation ID inside the ledger itself

Each choice changes availability, storage, and operational recovery. None removes the need to decide what an in progress record means after its owner disappears.

reservation answers: who may start?
recovery answers:    what already happened?

That second question is where production reliability lives.

18 / The part that generalizes

The General Lesson Is Reconciliation

Idempotency is often introduced as duplicate suppression. That description is too small. The mechanism reconciles two parties after communication becomes ambiguous: the client retains the name of its intention, and the server retains the result associated with that name.

wrong model: a retry is another request to perform work
right model: a retry asks for the result of named work

The same idea appears anywhere delivery can repeat while effects must not: provisioning, order creation, job submission, and message handling. The transport may deliver again. The business operation still needs a stable identity.

The safest retry is not the one that guesses whether the first call failed. It is the one that never needs to guess.
