Consistent Hashing Saves the Cache When Servers Move

Modulo hashing hides membership inside division. A consistent hash ring keeps the coordinate system stable when the server list changes.

Part 1

The Obvious Cache Shard Starts With Modulo

The schema more or less writes itself. A key arrives. The cache has a list of servers. Hash the key, divide by the server count, and use the remainder.

Java
Server owner(String key) {
    int slot = Math.floorMod(hash(key), servers.size());
    return servers.get(slot);
}

That code is sympathetic because it has the right local properties. It is deterministic. It is fast. With a stable server list, it spreads traffic well enough.

Trace
hash(cart:7) % 10 = 3
hash(cart:8) % 10 = 6
hash(cart:9) % 10 = 1

The mistake is not in the hash. The mistake is hiding membership inside the divisor.

Modulo treats the server list as if it were a constant. In real systems, membership is one of the least constant things in the room. Machines leave for deploys, hardware faults, capacity shifts, kernel upgrades, and plain bad luck. A shard function that changes meaning whenever the list changes is calm only during the part of the story that is already easy.

Part 2

The Divisor Is The Hidden Dependency

Remove one cache server and the divisor changes. The key did not change. The hash did not change. Almost every remainder did.

Trace
before: hash(key) % 10
after:  hash(key) % 9

same key
new remainder
new server

In the local Spring Boot benchmark, removing one node from a 10 node modulo map moved 89.9740 percent of 200,000 synthetic cart keys. That number is local evidence from the repo, not an Amazon production number.

Trace
mode    event   nodes   moved
modulo  remove  10 -> 9 89.9740%

The cache did not lose one server. It lost the warmed map.

That distinction matters because misses are not evenly painful. A cold cache often pushes work into the slower system it was protecting. The database sees the recovery event as fresh demand, even though user traffic may not have increased at all. The outage can therefore be caused by arithmetic that looked harmless in code review.

Part 3

Dynamo Turns The Server List Into A Ring

Amazon's Dynamo paper says the system hashes keys into a fixed circular space. Section 4.1 says Dynamo applies MD5 to generate a 128 bit identifier. Section 4.2 says the range is treated as a ring.

Trace
0 ------------------------------------------------ 2^128
^                                                |
|________________________________________________|

The server count is no longer part of the formula. A node owns positions on the circle. A key lands somewhere on the same circle.

Trace
key hash
   |
   v
---x---------A---------B---------C---------D------
             ^
             first node clockwise owns it

This sounds like ceremony until membership changes.

The ring gives the system a stable vocabulary. Keys do not belong to array indexes anymore. They belong to intervals. Membership changes can then be described as interval transfer, which is the kind of operation a storage system can test, audit, throttle, and retry.

Part 4

A Key Walks Clockwise Until It Finds An Owner

The core rule is small enough to fit in one function. Hash the key. Find the first token greater than that hash. If none exists, wrap around.

Java
String owner(String key) {
    long h = hash64(key);
    var token = tokens.ceilingEntry(h);
    return token == null ? tokens.firstEntry().getValue()
                         : token.getValue();
}

The ring makes ownership a property of ranges, not array indexes.

Trace
(A, B] -> B
(B, C] -> C
(C, D] -> D

That is the useful shift. The key map can survive a changing server list because the coordinate system stays fixed.

This is also why consistent hashing shows up in caches, storage systems, and routers. The point is not that a circle is magical. The point is that the circle is independent of the number of live machines currently serving it.

Part 5

One Leaving Node Should Only Move Its Own Range

Dynamo's section 4.2 states the principle advantage: a node's departure or arrival affects its immediate neighbors while other nodes remain unaffected.

Trace
before: A ---- B ---- C ---- D
after:  A ---------- C ---- D

B's range moves.
C and D keep their old ranges.

The local benchmark with 200 virtual nodes per physical node measured 10.4490 percent movement when one node left a 10 node ring.

Trace
mode             event   vnodes  moved
consistent-ring  remove  200     10.4490%

That is the whole cache story. A 10 node cache loses roughly one node's share instead of almost everything.

The exact percentage depends on the token placement and the key sample. The invariant is more important than any one run: keys outside the departed ranges keep the same owner. That invariant is what modulo hashing cannot offer.

Part 6

Virtual Nodes Make One Machine Look Like Many

The basic ring has a problem. If every machine gets one random position, the ranges can be wildly uneven.

Trace
A----------------------B--C-------D
|        huge A range       tiny C |

Dynamo addresses this with virtual nodes. Section 4.2 says each node gets multiple positions, called tokens. The physical machine owns all of its token ranges.

Trace
A1---B1---C1---A2---D1---B2---C2---D2---A3

Now a leaving machine gives up many small ranges, not one large range.

Virtual nodes also make capacity a dial. A larger machine can receive more tokens. A smaller machine can receive fewer. The paper calls out this heterogeneity benefit explicitly, because real fleets rarely contain perfectly identical machines for long.

Part 7

More Tokens Trade Metadata For Smoother Load

The trade is not free. More virtual nodes mean more membership metadata and more token maps to gossip or refresh.

Trace
few tokens:
A owns one unlucky huge range

many tokens:
A owns many smaller scattered ranges

Dynamo's section 6.2 compares partitioning strategies on a system with 30 nodes and N=3. The paper says Strategy 3 improved efficiency and reduced membership information by three orders of magnitude compared with Strategy 1.

Trace
Strategy 1: random tokens decide ranges
Strategy 3: fixed partitions decouple placement

The lesson is not "always add tokens." The lesson is to separate stable partitions from changing placement when the system grows up.

Part 8

The Local Run Makes The Failure Visible

The repo maps 200,000 synthetic cart keys onto 10 nodes. Then it removes and adds nodes using modulo hashing and the ring.

Trace
mode,event,nodes_before,nodes_after,virtual_nodes_per_node,
keys,moved_keys,moved_percent,min_load_percent,
max_load_percent,load_efficiency

The removal contrast is the headline.

Trace
modulo remove:          89.9740% moved
ring remove, 200 tokens: 10.4490% moved

The add path tells the same story.

Trace
modulo add:             90.9350% moved
ring add, 200 tokens:    9.3160% moved

Those numbers come from the default ./gradlew bootRun output.

Part 9

The Useful Number Is Movement, Not Hash Speed

Hashing speed is the wrong benchmark for this idea. The system is protecting cache locality during membership changes.

Trace
bad question:
how fast is the hash?

better question:
how much ownership changes?

The benchmark also reports the hottest node after the change. With 200 virtual nodes per machine, the hottest node after removal held 12.2955 percent of keys.

Trace
10 nodes -> 9 nodes
ideal after removal:  11.1111%
measured hottest:     12.2955%

That is not perfect balance. It is a workable trade for keeping the cache warm.

The benchmark intentionally reports movement and skew together. Movement alone can make a broken ring look good. Skew alone can make modulo look fine before the first membership change. The pair tells the actual operational story.

Part 10

The Real Code Is Almost The Whole Trick

The implementation is intentionally small. A sorted map stores token positions. Lookup is a ceiling search.

Java
Map.Entry<Long, String> entry = tokens.ceilingEntry(hash);
if (entry == null) {
    entry = tokens.firstEntry();
}
return entry.getValue();

The modulo baseline stays in the repo because it is the bug in executable form.

Java
int index = Math.floorMod(hash(key), nodes.size());
return nodes.get(index);

A mechanism article is stronger when the wrong version is runnable too.

The implementation avoids networking on purpose. Adding HTTP would make the demo feel more realistic while hiding the one property under test. The useful artifact is the ownership table before and after membership changes.

Part 11

Membership Becomes A Thing You Operate

Consistent hashing does not delete complexity. It moves complexity from every key lookup into membership management.

Trace
tokens must be:
chosen
persisted
gossiped
refreshed
rebalanced

Dynamo's paper makes that cost visible. Clients may poll a random Dynamo node every 10 seconds for membership updates, according to section 6.4. Section 6.2 also says one refined strategy required coordination when membership changed.

Trace
less key movement
more explicit membership state

That is a good trade only when warm ownership matters.

There are systems where it does not matter. If every request is cheap, stateless, and recomputable, modulo may be perfectly fine. Consistent hashing earns its keep when moving ownership has a real cost: cache warmth, disk transfer, replica repair, or downstream load.

Part 12

Build The Dumb Version Yourself

Build the smallest thing that proves the property.

Trace
1. implement modulo ownership
2. implement ring ownership
3. generate deterministic keys
4. remove one node
5. count changed owners
6. write the CSV

Do not start with replication, quorum reads, hinted handoff, or vector clocks. Those are Dynamo ideas too. They are not needed to see why the ring exists.

Shell
./gradlew bootRun
./gradlew test

The repo should make the central claim executable before it tries to look complete.

Part 13

Then Break It

The adversarial tests are more important than the happy path.

Trace
remove one server
add one server
use one virtual node
use many virtual nodes
verify removed nodes own nothing
verify the CSV is written

The one token test is deliberately ugly. In the local run, one virtual node per machine left the hottest node with 27.4315 percent of keys after removal.

Trace
consistent-ring remove, 1 token:
moved:        2.7995%
hottest node: 27.4315%

Low movement alone can be a trap. A ring that barely moves keys but overloads one survivor is still a bad ring.

Part 14

The Part That Generalizes

The larger lesson is that scalable systems often make the hidden coordinate system explicit. Modulo hashing smuggles membership into arithmetic. Consistent hashing gives membership a shape the system can change deliberately.

Trace
wrong model:
server = hash(key) % current_server_count

better model:
key position stays fixed
membership moves around it

Stable ownership is not magic. It is membership made explicit.
