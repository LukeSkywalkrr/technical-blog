Start here: reading the question

Requirement → techniqueMust explainDone
Problem

in a well-written question, every requirement points at a technique. Missing the hint means missing the design.

Map
  • "p99 under a few ms on every request" → in-memory copy inside the service (no network hop)
  • "keeps working when X is down" → local copy + disk snapshot + safe defaults
  • "changes reach everyone within N s" → push (SSE / pub/sub) + polling backup + versions
  • "never lose, never double-count" → durable log + idempotency + reconciliation
  • "same user, same result" → deterministic hash of the user ID
  • "huge writes" → append-only, batching, queue in front, LSM store, sharding
  • "huge reads, same answer" → precompute + cache + CDN
  • "spikes / flash sale" → queue, waiting room, load shedding, autoscale
  • "money, seats, inventory" → SQL transaction / conditional write / unique constraint
  • "DB update must also publish an event" → transactional outbox / CDC
  • "message processed twice" → idempotent consumer
  • "workers might both own a job" → lease + fencing token
  • "read and write needs differ a lot" → CQRS / materialised read view
  • "counts / trending / top K" → stream windows (+ sketches if approximate)
  • "search text" → inverted index · "near me" → geo index · "big files" → presigned multipart upload
  • "real-time to users" → websocket / SSE + connection registry + pub/sub
Use when

first 2 minutes of every question: underline each requirement and name its technique.

Latency numbersMust explainDone
Numbers

hashmap in your process ~100 ns · 1 MB from memory ~10–50 µs · SSD read ~100 µs · same-DC network round trip ~0.5 ms · Redis GET ~0.3–1 ms, p99 1–5 ms · indexed DB query 1–10 ms · cross-region 50–150 ms · HDD seek ~10 ms.

Rule

a budget under ~2 ms at p99 leaves no room for a network call → in-process.

Back-of-envelope mathsMust explainDone
Time

1 day ≈ 10⁵ s → 1M/day ≈ 12/s · 1B/day ≈ 12k/s · peak 2–3× (10× for launches).

Sizes

ID 8–16 B · row ~1 KB · photo 0.2–2 MB · 1 min HD video 50–100 MB.

One box

API server 10k–50k req/s · Postgres 5k–10k writes/s · Redis ~100k ops/s · Kafka partition ~10 MB/s · websocket server 100k–1M connections.

Watch out

always say what the number decides ("400k writes/s → in memory and sharded").

Choosing a datastoreMust explainDone
How

Postgres for transactions, relations, constraints (money, orders, users) · Cassandra / DynamoDB for huge writes read by one key · Elasticsearch for text / geo search (never the source of truth) · S3 for files · time-series DB for metrics · OLAP (ClickHouse) for analytics · Redis for speed, not truth.

Say it as

"Postgres for X because…, Cassandra for Y because…".

Data model in 5 stepsMust explainDone
How
  1. Entities = the nouns in the requirements.
  2. Access patterns = the exact queries ("list a user's bookings by date").
  3. Partition key = what you look up by · sort key = how you list (time) · secondary index for the rest.
  4. Unique constraints for "only one" rules (one review per user, idempotency keys).
  5. Denormalise for reads (counters like num_reviews on the parent).
Watch out

write it as columns, types and keys, not a paragraph.

API design checklistMust explainDone
How

nouns + HTTP verbs (POST /flags, GET /flags/{key}, PATCH, DELETE); non-CRUD actions as sub-resources (POST /flags/{key}/kill) · show key body fields with types · Idempotency-Key on creating POSTs · cursor pagination (?cursor&limit → nextCursor) · 202 + status URL for long work · /v1/ versioning · 409 on version conflict (If-Match) · auth in a header, never "who am I" in the body · name real-time channels (SSE /v1/stream).

Status codes

200 · 201 · 202 · 400 · 401 · 403 · 404 · 409 · 429 · 5xx.

Watch out

4–6 endpoints, one line each, then move on.

Session 1: Distributed caching

Cache layers and L1/L2Must explainDone
Problem

repeated reads are slow and load the DB.

How

browser → CDN → gateway → L1 (in-process memory, e.g. Caffeine, ~µs) → L2 (shared Redis, ~1 ms) → DB (the truth).

Watch out

L1 is per instance, so instances can disagree for a while; keep it small and bounded by TTL.

Use when

L1 for small hot read-mostly data (config, flags, rules); L2 for large shared data (profiles, sessions, feeds).

Cache-aside (lazy loading)Must explainDone
How
  1. Read Redis user:123.
  2. Hit → return.
  3. Miss → read the DB → SETEX user:123 300 … → return.
Watch out

the app owns the logic (Redis doesn't know your DB); first read is slow.

Use when

the default answer for profiles, products, metadata.

Read-through and write-throughMust explainDone
Read-through

the app calls cache.get(id); the cache library calls a configured loader on a miss. Same as cache-aside, logic hidden.

Write-through

writes go through the cache layer, which writes the DB synchronously and updates the cache.

Watch out

cache and DB still aren't one atomic transaction; handle failures and ordering.

Write-behind (write-back)Draw + trade-offsDone
How

write to the cache / a buffer now, flush to the DB later in batches.

Watch out

data acknowledged but only in memory is lost if the node crashes. Never for payments.

Use when

counters, likes, view counts, aggregations.

Refresh-ahead and prewarmingDraw + trade-offsDone
How

reload popular keys before they expire, or load the hot working set at deploy / before a known spike.

Use when

config, hot products, trending lists, predictable peaks.

TTL techniquesMust explainDone
Absolute

expires N s after insert (product data). Sliding: renewed on access (sessions).

Soft + hard

past soft TTL (30 s) serve stale and refresh in the background; past hard TTL (5 min) must reload or fall back.

Jitter

270–330 s instead of 300 s, so keys don't expire together. Doesn't help one super-hot key.

Negative

cache "not found" briefly. Stale-while-revalidate: serve stale, refresh async. Stale-if-error: serve stale when the source is down.

Versioned / generational keys

bump v7 → v8 in the key; old keys become unreachable (bulk invalidation).

Tombstone TTL

keep a delete marker for a while so a late copy doesn't resurrect deleted data.

Watch out

expiry isn't instant deletion everywhere (DynamoDB TTL deletes lazily, up to days later) → check expiresAt on read when it matters.

Invalidation on writeMust explainDone
How
  1. Update the DB (the truth).
  2. Delete the Redis key (delete, don't set: two setters can land in the wrong order).
  3. Publish "user:123 changed, v8".
  4. Every instance evicts its L1 copy.
  5. Next read reloads fresh data.
Watch out

DB and cache can't be updated atomically; use an outbox / CDC if the invalidation must never be lost.

The invalidation raceMust explainDone
Problem

reader misses and reads old v7 → writer commits v8 and deletes the key → reader writes v7 into the cache. Stale despite the delete.

Fixes
  • short TTL (bounds it; eventual only)
  • delayed double delete (delete again after a moment; reduces, doesn't guarantee)
  • generation check: loader reads the generation first and only installs if it's still current (atomic compare)
  • versioned writes: never replace v9 with v7
  • strongly consistent path: read the DB directly for data that must be exact
Watch out

pub/sub alone never guarantees cache = DB.

Missed invalidationsMust explainDone
Problem

an instance was disconnected when the invalidation was published and keeps serving stale data.

How

bounded L1 TTL · versions on every entry · on reconnect, clear L1 (or reconcile) · durable event log (replayable) instead of fire-and-forget pub/sub · periodic "latest version?" poll.

Redis client-side cachingDraw + trade-offsDone
How

client enables CLIENT TRACKING → Redis remembers which keys that connection read → on change, Redis sends an invalidation → SDK drops its local copy. Broadcast mode tracks by key prefix (less server state).

Watch out

only knows about changes made in Redis, not direct SQL updates.

How a two-level cache SDK worksDraw + trade-offsDone
get(key)

L1 (Caffeine) → miss: Redis → miss: DB loader → fill Redis and L1 → return.

on invalidate(key, version)

ignore older versions · evict L1 · mark in-flight loads stale so they can't reinstall old data (load epoch).

on disconnect

clear untrusted L1 entries · reconnect and re-enable tracking.

Also does

connection pools, memory limits, cluster routing, retries, coalescing, serialisation, metrics.

Cache stampedeMust explainDone
Problem

a hot key expires; thousands of requests miss together and hammer the DB.

How

singleflight (one loader per key per process, others wait for its result) · refresh lease across servers (SET lease:key NX PX 3000, winner reloads, others wait or serve stale) · early / probabilistic refresh · jitter · prewarm.

Watch out

a refresh lease controls who reloads the cache, not who may change business data.

Hot keysMust explainDone
Problem

one key (viral post, celebrity, flash-sale item) exceeds one Redis shard.

How

copies key#1…key#N on different shards, readers pick one · L1 in-process cache in front · detect by sampling access counts.

Watch out

consistent hashing balances keys, not traffic: it can't fix one hot key.

Eviction and sizingMust explainDone
How

LRU (default) · LFU (stable popularity) · FIFO / TTL-based. Size for the hot set: ~20% of data serves ~80% of reads.

Session 2: Feeds and read optimisation

Fan-out on write (push)Must explainDone
How

on post, ZADD feed:{follower} {score} {postId} for every follower (capped list).

Trade-off

instant reads · huge write amplification for authors with millions of followers.

Fan-out on read (pull)Must explainDone
How

on read, fetch followed authors → their recent posts → merge, sort, top 20.

Trade-off

cheap writes · slow reads for users following thousands.

Hybrid fan-outMust explainDone
How

push for normal authors; for authors above a follower threshold, pull their posts at read time; merge, dedupe, filter, rank.

Also

skip inactive users when pushing; rebuild their feed on login.

Use when

the standard answer to "celebrity" in any feed / inbox / activity stream.

Feed pipeline: candidates → rank → hydrateDraw + trade-offsDone
How
  1. Candidate generation: cheaply gather a few hundred plausible post IDs.
  2. Light scoring, then an expensive ranker on the top few.
  3. Hydrate: fetch bodies, authors, media in batches (feeds store IDs only).
  4. Read-time filters: privacy, blocks, deleted posts.
Watch out

precompute top-N asynchronously so a read doesn't redo the work.

Cursor pagination and stable sessionsMust explainDone
How

cursor = last (score, ID) instead of OFFSET → no shifting as new items arrive. For ranked feeds whose scores change while scrolling, snapshot the order per session (session / ranking-version ID).

Deletes and privacy in feedsDraw + trade-offsDone
How

don't remove one celebrity post from millions of timelines synchronously. Mark it deleted, filter at hydration, clean up timelines asynchronously.

Precomputed read models, materialised views, CQRSDraw + trade-offsDone
Problem

many readers ask the same expensive question; read and write shapes differ.

How

maintain the answer on write (Redis sorted sets for leaderboards / trending / per-category feeds; counters on rows; DB materialised views). CQRS = a separate write model and read-optimised projections fed by events.

Trade-off

more write work and storage; read model lags slightly.

Counting at scaleDraw + trade-offsDone
How

sharded counters (N sub-counters, sum on read) · batch increments (in memory / stream, write every few s) · per-minute buckets for windows · HyperLogLog for unique counts (~1% error, KBs) · count-min sketch for frequencies / top K · stream + batch reconciliation for exact big counts.

Session 3: Sharding, replication and indexes

Sharding strategiesDraw + trade-offsDone
 

Hash hash(id) % N: even spread; changing N remaps almost everything.

 

Range (A–F, G–M, by date): cheap range queries; hot ranges ("today").

Directory

lookup table tenant → shard; flexible; the directory is a dependency.

Geographic

by region; low latency; cross-region queries are hard.

Choosing the key

the field almost every query filters by, high cardinality, even traffic.

Consistent hashing and virtual nodesDraw + trade-offsDone
How
  1. Hash nodes onto a ring.
  2. Hash each key onto the same ring.
  3. Key belongs to the next node clockwise.
  4. Adding a node moves only the keys in its new interval (~1/N).
  5. Virtual nodes: each machine owns many small ranges → better balance.
Watch out

still can't fix a single hot key.

Hot shards and reshardingDraw + trade-offsDone
Hot key split

likes:post9#0…#15, sum on read (more write capacity, harder reads).

Resharding online

dual-write to old and new → backfill → verify → switch reads → stop old writes; forward requests for moved keys; avoid two owners during the move.

Leader–follower replicationMust explainDone
How

writes to the leader; followers replay its log; reads can go to followers.

Sync vs async

sync waits for replica acks (no loss, slower); async acks first (fast, may lose the last writes on failover).

Failover

promote a follower; fence the old leader (epochs) so it can't keep writing.

Read-your-writes and monotonic readsDraw + trade-offsDone
Problem

replica lag shows users stale data, even their own change.

How

read-your-writes: read from the leader for a few seconds after a user writes, or until the replica reaches the write's version. Monotonic reads: pin a user to one replica so they never go backwards.

Quorums and leaderless replicationDraw + trade-offsDone
How

N replicas; write to W, read from R; R + W > N means the sets overlap (N=3, W=2, R=2). Read repair fixes stale replicas found during reads; anti-entropy syncs in the background.

Watch out

overlap alone isn't full linearisability (concurrent writes, sloppy quorums).

Multi-leader and conflictsRecogniseDone
How

several sites accept writes; conflicts resolved by last-writer-wins (loses data), vector clocks (detect concurrent versions), or CRDTs (merge automatically; collaborative / offline apps).

Use when

multi-region writes, offline-first clients.

IndexesMust explainDone
How

B-tree for equality + ranges · composite index serves its leftmost columns ((user_id, created_at)) · covering index avoids touching the table · inverted index for text · geo index for location · LSM tree (Cassandra, RocksDB) for write-heavy vs B-tree (Postgres) for read-heavy.

Watch out

every index slows writes.

Session 4: Consistency and concurrency

Idempotency keysMust explainDone
Problem

retries repeat side effects (double charge, duplicate order).

How

client sends a unique key → server stores (key → result) under a unique constraint → a repeat returns the stored result.

Use when

payments, orders, any POST that's retried.

Optimistic locking, CAS, conditional writesMust explainDone
How

UPDATE docs SET content=:c, version=6 WHERE id=:id AND version=5 → 0 rows = someone else won → retry / 409. CAS = set only if the value still equals the expected one. Conditional write = qty = qty - 1 WHERE qty > 0.

Use when

conflicts are rare; state transitions; counters.

Pessimistic lockingMust explainDone
How

SELECT … FOR UPDATE locks rows until commit.

Use when

conflicts are common (hot seat, account balance); lock in a fixed order to avoid deadlocks.

Version numbers for propagationMust explainDone
Problem

updates arrive twice, late, or out of order; copies drift.

How

every change gets an ever-increasing version; receivers apply only newer versions; a periodic "latest version?" check repairs anything missed.

Use when

config / flag propagation, cache updates, device sync. (The missing answer in the feature-flag round.)

Distributed lock with RedisMust explainDone
How

SET lock:job42 {uniqueToken} NX PX 10000 (acquire if absent, expire in 10 s) → do the work → release with a Lua script that deletes only if the token still matches.

Watch out

a paused holder can lose the lock and still write → fencing tokens.

Fencing tokensMust explainDone
How

the lock service hands out increasing tokens (41, then 42). The resource remembers the highest token seen and rejects writes with an older one, so a stale holder (41) is refused after 42 has written.

Use when

"two workers might both think they own the job".

Leases, leader election, epochsDraw + trade-offsDone
How

a leader holds a lease renewed by heartbeats (ZooKeeper / etcd); if it stops renewing, another node takes over. Each new leader gets a higher epoch; operations from older epochs are rejected.

Consistency modelsDraw + trade-offsDone
How

strong (every read sees the latest write; money, inventory, uniqueness) · eventual (copies converge; feeds, likes, search) · read-your-writes · monotonic reads.

CAP / PACELC

during a partition choose consistency or availability; otherwise choose latency or consistency.

Logical clocks, vector clocks, CRDTsRecogniseDone
How

Lamport clocks order events by causality but can't detect concurrency · vector clocks track per-writer histories to detect concurrent versions · CRDTs are data types whose replicas always merge to the same result.

Use when

recognise; deep-dive only for collaborative editing / offline sync.

Session 5: Kafka and reliable events

Queue vs log vs pub/subMust explainDone
Queue (SQS, RabbitMQ)

each message to one worker, deleted when done; visibility timeout; DLQ → distributing work.

Log (Kafka)

retained, ordered per partition, many consumer groups each read everything, replayable → event streams, pipelines.

Pub/sub (Redis)

pushed to current subscribers, nothing stored → real-time fan-out to online servers.

Kafka partitions and orderingMust explainDone
How

producer key (e.g. paymentId) → hash → partition. Order is guaranteed only within a partition, so all events of one entity share a key.

Watch out

a hot key = a hot partition; more partitions = more parallelism.

Consumer groups and offsetsMust explainDone
How
  1. Each partition goes to one consumer in the group.
  2. Consumer polls a message.
  3. Does the work.
  4. Commits the offset after the effect is durable.
  5. Crash before commit → message redelivered → the effect must be idempotent.
Delivery guaranteesMust explainDone
How

at most once (may lose; metrics sampling) · at least once (may duplicate; default) · effectively once = at least once + idempotent consumer · exactly once only within one transactional scope (Kafka-to-Kafka transactions, Flink checkpoints).

Say it as

"at least once plus idempotency".

Idempotent consumer / inbox tableMust explainDone
How

store processed event IDs (unique constraint) in the same transaction as the effect; skip IDs already seen. Or make the effect naturally idempotent (upsert, version check).

Transactional outboxMust explainDone
Problem

"update SQL and publish to Kafka" can half-succeed.

How

in one DB transaction, write the business row and an outbox row → a relay / CDC reads committed outbox rows → publishes to Kafka → marks them sent. Consumers still dedupe.

Change data capture (CDC)Draw + trade-offsDone
How

a connector (Debezium) reads the DB's commit log (Postgres WAL, MySQL binlog) and publishes every change. Feeds search indexes, caches, analytics without touching app code.

Watch out

downstream lag; schema changes must be handled.

DLQ, retry queues, poison messagesMust explainDone
How

failed message → retry queue with a delay (backoff) → after N tries → DLQ for inspection and replay. One bad message must never block the partition.

Backpressure and batchingDraw + trade-offsDone
How

bounded queues; slow or reject producers when consumers fall behind; scale consumers on lag. Batch by count or time (500 msgs / 1 s) to trade a little latency for throughput.

Replay and log compactionDraw + trade-offsDone
How

replay = reset a consumer group's offset to reprocess history (fix a bug, build a new view). Compaction keeps only the latest value per key (a changelog / current state per entity).

Event sourcingRecogniseDone
How

store events as the source of truth; current state = replaying them into projections. Full audit and time travel; harder queries and schema evolution.

Session 6: Workflows, scheduling and expiry

SagaDraw + trade-offsDone
How

a multi-service operation as local transactions, each with a compensating action: hold room → charge → confirm; if charge fails → release room. Orchestrated (one coordinator) or choreographed (events).

Watch out

avoid two-phase commit across services (blocking, slow).

Delayed jobsMust explainDone
How

delay queue (SQS delay) · Redis sorted set scored by run time (ZADD scheduled_jobs 1730000000 job123; workers atomically claim due jobs) · time-bucketed table (executions partitioned by hour; a watcher loads the next bucket into the delay queue).

Watch out

claims need ownership, retries and crash recovery.

Durable scheduler with leasesDraw + trade-offsDone
How

jobs persisted in a DB; a worker claims a job with a lease (visibility timeout / locked_until), heartbeats while running, acks when done; an expired lease lets another worker take it. Recurring jobs compute the next run after each one.

Timing wheelRecogniseDone
How

a circular array of time buckets; each tick processes one bucket; hierarchical wheels cover long ranges. Efficient for millions of near-future timers (Kafka, Netty use it).

Expiry: holds and TTL deadlinesMust explainDone
How

persist expiresAt → async release job / sweeper (index on expiry) → and check expiresAt inside the confirming transaction. The job keeps things tidy; the transaction check keeps them correct even when the job is late.

Reconciliation workerMust explainDone
How

periodically compare expected vs actual (ledger vs bank, aggregates vs raw logs, outbox vs published, SDK version vs latest) and repair: missed events, stuck transactions, failed syncs.

Use when

anything that must be correct.

Workflow enginesDraw + trade-offsDone
How

Temporal / Step Functions persist each step's state, retry steps, and resume after crashes. Use for long multi-step processes (video processing, onboarding, payouts).

H. Session 7: APIs, traffic and resilience

Load balancingDraw + trade-offsDone
How

L4 (TCP; fast; long-lived connections like websockets) vs L7 (HTTP; route by path / header). Algorithms: round-robin · least connections · consistent-hash routing (key → stable owner).

Watch out

sticky sessions are a behaviour; consistent hashing is one way to implement them.

Service discovery, health checks, poolingDraw + trade-offsDone
How

instances register (Consul / Kubernetes DNS); health checks remove bad ones; clients reuse pooled connections instead of opening new ones per request.

API gatewayMust explainDone
How

the front door: TLS, auth, rate limiting, routing, request IDs, request/response shaping. A BFF (backend for frontend) aggregates several backends for one client.

Scatter-gather and hedged requestsRecogniseDone
How

scatter-gather queries all shards in parallel and merges (search, sharded reads). Hedged request: if a call is unusually slow, send a second copy elsewhere and take the first answer (only for safe reads).

Rate-limiting algorithmsMust explainDone
How

fixed window (bursts at edges) · sliding log (exact, memory heavy) · sliding window counter (approximate, cheap) · token bucket (bursts up to capacity; usual answer) · leaky bucket (smooth output; adds latency) · hierarchical limits (user + org + global), weighted costs, concurrency limits.

Response

429 + Retry-After.

Token bucket in RedisMust explainDone
How

per request, in one Lua script: tokens = min(capacity, tokens + elapsed × rate); if tokens ≥ cost → subtract, allow; else reject. Store tokens + last refill time per key with a TTL.

Watch out

many gateways update one bucket → must be atomic (Lua); shard Redis by key; decide fail-open vs fail-closed.

Timeouts, retries, retry budgetsMust explainDone
How

a timeout on every call and a deadline for the whole request (passed downstream) · retry only safe / idempotent calls · delay = random(0, min(cap, base × 2^attempt)) (backoff + jitter) · a retry budget caps extra traffic · retry at one layer only, never at every layer.

Circuit breakerMust explainDone
How

CLOSED (normal) → too many failures → OPEN (fail immediately, use fallback) → after cool-down → HALF-OPEN (a few probes) → success: CLOSED, failure: OPEN.

Watch out

combine with retries carefully; retries against a failing service make the outage worse.

Bulkheads, load shedding, admission controlDraw + trade-offsDone
How

separate thread pools / queues per dependency or priority (one slow dependency can't drain everything) · under overload, reject low-priority work first (503 / 429) · only accept work when capacity exists.

Graceful degradation and fail-open / fail-closedMust explainDone
How

serve stale data, a cached copy or a safe default instead of an error; turn off optional features. Decide per feature: fail open (allow) for UI tweaks and rate limits, fail closed (deny) for payments and security.

I. Session 8: Real-time systems

Polling vs SSE vs websocketsMust explainDone
How

polling (simple, wasteful) · long polling (held request until news) · SSE (server → client stream over HTTP; feeds, prices, status, config pushes) · websocket (two-way; chat, collaboration, games) · push notifications (APNs / FCM; app in background) · webhooks (server → server).

Connection registry and routingDraw + trade-offsDone
How

gateways hold the actual sockets in memory; a shared registry (Redis) maps user123 → gateway G7, connection 456; a delivery router (or a pub/sub channel per user that G7 subscribes to) sends each message to the right gateway.

Watch out

the registry holds locations, never the sockets themselves.

Heartbeats, presence, session epochsDraw + trade-offsDone
How

heartbeat every N s refreshes a key with a TTL → no heartbeat = offline / dead connection. Each reconnect gets a new session epoch so messages for the old session are rejected.

Reconnect and replayDraw + trade-offsDone
How

messages are stored durably first; the websocket is only a delivery channel. On reconnect the client sends its last acknowledged cursor and fetches everything after it. Delivery acks drive "delivered" status.

Slow clientsRecogniseDone
How

a bounded outbound queue per connection; if it fills, drop non-critical updates or disconnect (the client will resync on reconnect).

J. Session 9: Search and storage

Search index and syncDraw + trade-offsDone
How

inverted index (term → posting list of doc IDs) → intersect posting lists for multi-word queries → rank (BM25, recency, popularity). Keep it in sync from the DB via CDC / outbox.

Watch out

index lag: a deleted or permission-changed document can still match → check the source of truth before returning sensitive results.

AutocompleteDraw + trade-offsDone
How

prefix trie / edge n-grams / a search engine's completion index, with top suggestions precomputed per prefix and cached.

Geo indexesDraw + trade-offsDone
How

geohash (cell + 8 neighbours; Redis GEO, B-tree) · quadtree (splits by density; in memory) · H3 hexagons (equal neighbour distance; movement) · S2 (cover any shape) · R-tree (PostGIS / Elasticsearch, points + polygons). Narrow with the index, then compute exact distance.

Use when

moving things → Redis GEO with TTL; places and polygons → PostGIS / Elasticsearch.

Top-K and hybrid retrievalRecogniseDone
How

retrieve the best few without scoring every document (per-shard top K, then merge). Hybrid search = lexical (BM25) + vector search results merged, then a reranker on the small combined set.

Presigned, multipart, resumable uploadsMust explainDone
How

server signs a short-lived URL → client uploads parts straight to S3 in parallel → completed parts are recorded → after a drop, upload only missing parts → complete the multipart upload.

Use when

anything over a few MB; bytes never pass through app servers.

Content addressing, dedupe, manifestsDraw + trade-offsDone
How

chunk the file, hash each chunk (SHA-256) → the hash is the chunk's ID → server says which chunks it lacks → upload only those → a manifest lists the file version's ordered chunk IDs. Gives dedupe, resumability, delta sync, immutable versions (copy-on-write); garbage-collect unreferenced chunks later.

CDNMust explainDone
How

edge caches near users for static files, images, video segments and short-TTL public API responses. Pull CDN (fetch from origin on miss; default) vs push. Signed CDN URLs for private content; versioned file names (app.3f9c.js) instead of purges; range requests for video.

Media transcoding pipelineDraw + trade-offsDone
How

upload complete → event → split at keyframes into segments → transcode each segment × resolution in parallel → write outputs + manifest (HLS / DASH) to S3 → CDN → adaptive bitrate playback.

K. Session 10: Operations, scale and security

Stateless services and autoscalingDraw + trade-offsDone
How

no session state in app servers (tokens / Redis) → any server serves any request → scale out behind the load balancer on CPU, latency or queue depth (workers).

Multi-region, RPO and RTODraw + trade-offsDone
How

active-passive (simple; failover takes time) vs active-active (fast; needs conflict handling); GeoDNS to the nearest healthy region. RPO = how much data you may lose (async replication loses a little); RTO = how fast you're back. They're separate guarantees.

ObservabilityDraw + trade-offsDone
How

RED metrics for services (rate, errors, duration) · USE for resources (utilisation, saturation, errors) · structured logs with request IDs · distributed tracing · SLOs + error budgets · alerts on symptoms.

Safe deploymentsRecogniseDone
How

canary (small % first) · blue-green (switch between two environments) · feature flags (deploy dark, enable later; local SDK evaluation) · shadow traffic (copy real requests to a new path without side effects).

Security patternsDraw + trade-offsDone
How

authentication (who you are) vs authorisation (what you may do; RBAC / ABAC) · short-lived access tokens + rotating refresh tokens · session versions to revoke early · mTLS between services · signed URLs that expire · replay prevention (nonce + timestamp + request ID) · per-tenant isolation and quotas · encryption + key rotation · audit logs.

Watch out

every path (search, caches, feeds) must still apply authorisation.

Consensus (Raft / Paxos)RecogniseDone
How

replicas agree on one ordered log despite failures by majority vote and a single elected leader per term. Used inside ZooKeeper, etcd, Kafka's controller.

Use when

recognise and name it; you use these systems rather than implement them.
